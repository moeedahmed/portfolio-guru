### Two real defects found

**A. A doctor who says "all domains" cannot get All Domains, and gets re-asked.**
`derive_domains_from_source` has no pattern that matches the phrase "all domains", and
`_ALL_DOMAINS_MIN_EVIDENCED` requires 3+ evidenced domains plus a department-wide cue.
`resolve_esle_domains` returns `[]` when nothing is evidenced, even when the doctor's own
words name the option. Because `domains_of_performance` is now `required: True`, an empty
value is a blocking pre-draft gap (`bot.py:5644 _pre_draft_completeness_gaps` →
`_ask_pre_draft_completeness`), and there is no ask-once flag across its ~10 call sites.
So the doctor is asked, answers "all domains", and is asked again. Fixing.

**B. `ESLE_2021` skips the exclusivity re-normalisation at filing time.**
`normalise_fields_for_deterministic_filing` strips the `_2021` suffix, so `handling_key`
is `"ESLE"`, which is not in the `("ESLE_PART1_2", "ESLE_ASSESS")` tuple — yet
`_FORM_FIELD_MAP_VARIANT_BASES` (`kaizen_form_filer.py:1565`) routes `ESLE_2021` to the
`ESLE_PART1_2` field map, including the domains widget. A restored/edited 2021-variant
draft could reach the widget with `All Domains` plus individual domains. Fixing.

## 12 — Root cause: the code only recognises an option spelled `n/a`, and this one is not

Moeed's live observation is that the option offered is **"Not applicable"**. Two independent
string tests in the existing code both fail on that spelling:

```
$ python3 -c "... re.compile(r'n/?a', re.I) ..."
'Not applicable' hasNa=False  partial-match('- n/a -')=False
'- n/a -'        hasNa=True   partial-match=True
'N/A'            hasNa=True   partial-match=False
```

- The candidate filter requires `hasNa: options.some(o => /n\/?a/i.test(o.text))`
  (`kaizen_form_filer.py:2580`). "Not applicable" has no `na` substring, so the widget is
  filtered out before anything is attempted.
- Even past that filter, `_fill_select(page, dom_id, "- n/a -")` (`:2426` on main) tries exact
  label, then value, then `"- n/a -" in option.lower()`. All three fail on "Not applicable".

So the dropdown was never touched, and a blank required control was reported as a clean save.
The same bug silently affects every other form carrying this widget, not just ESLE.

## 13 — Fix made

New `backend/procedural_skills.py`: recognises every seen spelling of the no-procedure option
(`- n/a -`, `N/A`, `NA`, `Not applicable`, `None`), and resolves which option to select from
the labels the page actually rendered — a stated skill field first, then a skill the session's
own words name, otherwise the not-applicable option. Returns `None` only when the control
offers neither, which is a real gap.

`backend/kaizen_form_filer.py`: `_default_non_applicable_procedural_selects` →
`_resolve_procedural_skill_selects(page, form_type, fields)`. The page script no longer decides
anything; it reports each blank procedural dropdown's rendered options and Python picks. It
returns `(answered, unresolved)`, and an unresolved control is now surfaced — `errors` on the
`fill_kaizen_form` path, `skipped` on `file_to_kaizen` — both of which downgrade the result to
`partial` instead of a clean save. Variant gating moved from `canonical_form_type` to
`filing_form_base`, so `DOPS_ACCS_2021` and friends still require a real skill.
