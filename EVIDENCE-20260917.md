Worktree: `portfolio-guru-esle-routing`, branch `work/esle-routing`, base `5e23434`.
Appended as observations are made. No live bot, no Telegram send, no credentials read.

## 1. Explicit detection is broken for a case that names ESLE — CONFIRMED

Run (real output):

```
$ backend/venv/bin/python -c "... extractor.extract_explicit_form_type(...)"
case1: None
case2: None
case2 relaxed: ESLE_ASSESS
sle phrase: None
```

- Case 2 begins "I did a 45-minute ESLE…" and still returns `None` under the default
  `require_intent=True`. Cause: `esle` lives only in `secondary_codes`
  (`backend/extractor.py:843`), gated behind `intent_phrases`
  (`backend/extractor.py:829-835`). The list has `"do a"` but not `"did a"`, so no intent
  phrase matches and the function returns `None` at `backend/extractor.py:838`.
- `"supervised learning event"` matches nothing at all — confirmed by the `sle phrase: None`
  line above. The only ESLE primary phrase is `"significant learning event"`
  (`backend/extractor.py:803`), which is a _different_ thing and is explicitly called out as
  a non-trigger in the recommender prompt (`backend/extractor.py:2169`).
- Passing `require_intent=False` does return `ESLE_ASSESS`, proving the code key itself is
  wired; only the gating is wrong.

## 2. Form key topology

- `backend/extractor.py:407` aliases user-facing `"ESLE"` → `"ESLE_ASSESS"`; `:416` aliases
  `"ESLE_2021"` → `"ESLE_ASSESS"`. So the draft flow key is `ESLE_ASSESS`.
- `backend/form_labels.py:13-14`: both `ESLE_ASSESS` and `ESLE` display as "ESLE".
- `backend/form_schemas.py:461` (`ESLE_ASSESS`, "ESLE: Part 1 & 2") and `:882` (`ESLE`).

## 3. The two suspected blockers in the run card are NOT the cause — DISPROVEN

- `ESLE_ASSESS` is present in **every** profile catalogue in `TRAINING_LEVEL_FORMS`
  (`backend/bot.py:2568-2625`: ST3, ST4, ST5, ST6 and SAS all list it). The stage filter
  `_filter_recommendations_for_allowed_forms` (`backend/bot.py:2924`) keeps anything whose
  `form_type in allowed`, so it does not drop ESLE for a Higher trainee.
- `_OBSERVATION_BLOCKED_FORMS` (`backend/bot.py:2986`) is **not** a blocklist. Its only reader is
  `_profile_blocked_fallback_recommendations` (`backend/bot.py:2989`), which runs only when the
  profile has already blocked *every* recommendation; the set merely decides whether the CBD or
  the REFLECT_LOG fallback is listed first. It cannot remove ESLE from an otherwise-valid list.

So neither the stage list nor the blocked-form rule explains the missing ESLE.

## 4. A named form does bypass the recommender — so fixing detection is sufficient for case 2

`backend/bot.py:10368-10398`: the case-input handler calls
`extract_explicit_form_type(case_text)` and, on a hit, sets `chosen_form`, records an
`explicit_form_detected` audit event and renders that one form's keyboard — before any
profile filtering, artifact check or recommender call. Naming a form therefore already wins;
the defect for case 2 is purely that ESLE is not detected as named.

## 9. Unproven

- The live bot was not run and no Telegram message was sent. All behaviour above is proven
  offline against the real code paths, not observed in the product.
- The AI recommender prompt changes (rule 4 and the ESLE definition block) were **not**
  executed against Vertex AI — that needs credentials and a live model call. The offline
  guarantee for case 1 rests entirely on the deterministic `_ensure_esle_for_supervised_shift`
  post-processor, which runs regardless of what the model returns.

## 10. Residual risk

"Supervised learning event" is RCEM's *umbrella* term covering Mini-CEX, CBD, DOPS, ACAT and
ESLE, not just ESLE. Treating it as a primary ESLE phrase (as the run card directs) means a
doctor writing "I did a supervised learning event with my consultant" is routed to ESLE rather
than asked which SLE they mean. Mitigation in place: primary hits resolve earliest-then-longest,
so any other explicitly named form appearing earlier in the message still wins
(pinned by `test_another_named_form_still_wins_over_a_bare_mention`).
